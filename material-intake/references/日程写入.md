# 日程写入（日历 + 提醒）

材料里凡是能推出时间的事项——开庭、举证期限、上诉期、答辩期、会议通知、驻场安排——都走本模块，落成「日历事件 + 分档提醒」。macOS 直接写入系统日历与提醒事项；Windows 与其他系统导出标准日历文件导入。

## 一、先定三条底线

1. **只写带锚点的条目**。每条写入时会在备注末行留「来福ID: <锚点>」，读取、更新、撤销都按这一行整行匹配，绝不触碰你手工建的事件与提醒。
2. **同一锚点不重复**。写入前先按锚点查找，命中即更新，反复执行同一条清单不会产生重复条目。
3. **缺省只预演**。`plan` 只打印将要写入什么，加 `--apply` 才真正落盘。撤销同样先预演。

## 二、时间与提醒规则

| 事项类型 | 日历事件 | 提醒档位 | 提醒时点 |
|---|---|---|---|
| 开庭（hearing） | 写入，起止时间照材料 | 7、3、1、0 | T-7／T-3／T-1 当日 09:00；当天 07:30 |
| 期限（deadline） | 写入，默认落截止日 09:00、时长 30 分钟 | 7、3、1、0 | 同上 |
| 驻场（onsite） | 写入，无固定时段时写全天 | 7、3、1、0 | 同上 |
| 会议（meeting） | 写入，结束未知默认开始 +2 小时 | 1、0 | 前一日 09:00；当天 07:30 |
| 待办（task） | 默认不占日历 | 0 | 当天 07:30 |

补充规则：

- 已过期的档位自动跳过（例如今天才录入、开庭在下周，T-7 就不会补一条过期提醒）。
- 事件开始时间早于当天 07:30 时，当天提醒改为「开始前 90 分钟」，避免提醒晚于事项本身。
- 期限类若材料载明了具体时刻，用 `deadline_clock: true` 保留该时刻，不强制改成 09:00。
- 提醒标题按 `【T-7】类型｜案号·当事人` 生成，与日程标题同一套命名。

## 三、清单格式

录入时先生成一份 JSON 清单（模板见 `assets/日程清单模板.json`），再交给模块执行。

| 字段 | 必填 | 说明 |
|---|---|---|
| `kind` | 是 | `hearing`／`deadline`／`meeting`／`task`／`onsite` |
| `start` | 是 | `2026-10-14T09:20:00`；只写日期时按该类默认时点处理 |
| `case_no` | 建议 | 案号，进标题与备注 |
| `parties` | 建议 | 当事人，进标题与备注 |
| `title` | 否 | 没有案号与当事人时用作标题主体 |
| `label` | 否 | 覆盖默认类型标签（默认开庭／期限／会议／待办／驻场） |
| `end` | 否 | 缺省按上方规则推算 |
| `all_day` | 否 | 全天事件 |
| `location` | 否 | 地点，写入事件地点与备注 |
| `source` | 否 | 材料来源，写进备注便于回溯 |
| `basis` | 否 | 期限的推算依据（如「送达日 +15 日」），写进备注 |
| `notes` | 否 | 追加备注 |
| `offsets` | 否 | 自定义提醒档位，如 `[3,1,0]` |
| `calendar_event` | 否 | 默认 `true`；`false` 表示只建提醒、不占日历 |
| `anchor` | 否 | 不传则按内容自动生成，写入后回填 |

清单顶层可写 `calendar` 与 `reminder_list` 指定容器；命令行参数优先级更高。

## 四、命令

```bash
SW="python3 \"$SKILL/scripts/schedule_write.py\""

$SW doctor                                   # 平台、后端、授权、容器自检
$SW plan  --json 产出/日程清单.json            # 预演
$SW apply --json 产出/日程清单.json            # 写入（macOS）
$SW ics   --json 产出/日程清单.json --out 产出/日程清单.ics   # 导出日历文件
$SW list --days 60                           # 查出本模块写入的条目
$SW rm --anchor LR-MI-XXXXXXXX --apply        # 撤销该条目及其全部提醒档位
```

`--calendar` 与 `--reminder-list` 可指定容器，缺省为「工作」日历与「提醒」清单；容器不存在时 `apply` 会自动新建（新建在「本机」账户，iCloud 新日历在同步完成前写入会丢失，实测如此）。

## 五、macOS：权限与容器

后端是 `bin/lr_ek`（EventKit，源码 `bin/lr_ek.swift`）。首次运行会向宿主应用申请日历与提醒事项权限，授权入口在「系统设置 → 隐私与安全性 → 日历／提醒事项」，勾选正在运行本技能的宿主应用（Codex、WorkBuddy 或千问办公）。

**权限必须选「完全访问」，不能选「仅写入」。** 这是本模块唯一会让底线失效的配置：macOS 的「仅写入」下写入照样成功，但 `list_events`、`list_reminders`、`delete_*` 全部被拒，防重复与按锚点撤销同时失效，已写入的条目变成无法管理。2026-09-28 在千问办公上实测出现过这一现象，把权限改成「完全访问」后恢复正常。

因此 `doctor` 会实测读权限：读不通时打印「写入通道可用但读取被拒，不得直接 apply」，JSON 中 `ok:false`、`read_access:false`，退出码为 2。授权状态显示「已授权」只代表系统给了某项权限，不代表能读，判断一律看结论行。

`apply` 与 `rm` 在动作前做同一项体检：读权限不足时直接拒绝，并提示改用 `ics` 导出，避免写出无法查重、无法撤销的条目。

若换到 Intel 芯片的 Mac：随包二进制是 arm64，无法直接运行；装了 Xcode 命令行工具（`xcode-select --install`）后，模块会用 `bin/lr_ek.swift` 自动重编译一份。

## 六、Windows：三条通道＋手工兜底，按环境选

Windows 没有 EventKit，改用标准日历文件与日历客户端两条通道。

**两侧能力不一致，动手前先认清三点**（完整清单见 `references/依赖与注意事项.md` 第四节）：

1. **周期日程**：macOS 能建原生周期事件（EventKit `recurrenceRule`），Windows 与本模块导出的 `.ics` **都不支持重复规则**——需要重复日程时逐次生成，或导入后手工设为重复。
2. **撤销与读回**：macOS 一条 `rm --anchor` 全部支持；Windows 只有 `win_calendar.ps1` 与 `win_remind.ps1` 支持，**`.ics` 导入的条目只能在客户端按正文「来福ID:」手工搜删**——日程还会改动时不要走 `.ics`。
3. **到点提醒可靠性**：Windows 靠计划任务与系统通知，**关机或休眠期间到点不弹**，开机是否补弹由系统决定，不做保证，且受专注助手影响。

### 方案一：导出 .ics 后导入（通用，推荐先行）

```bash
python3 "$SKILL/scripts/schedule_write.py" ics --json 产出/日程清单.json --out 产出/日程清单.ics
```

生成的 `.ics` 是通用格式，带 9 档提醒的写法与 macOS 侧一致：

1. **桌面日历客户端**：双击文件 → 「添加到日历」→ 选目标日历 → 导入。约会与提醒一起进。
2. **Windows 日历应用**：双击 → 「添加到日历」。
3. **手机日历**：把 .ics 发到微信或邮箱，在手机上点开，用系统日历打开即可，提醒随文件带入。

对应关系：macOS 侧的「日历事件」等于 Windows 侧的约会；macOS 侧的「提醒清单档位」在 Windows 侧是约会自带的提醒（VALARM）。同一份 .ics 也可作为邮件附件发给同事，对方自行导入。

### 方案二：直写 Windows 系统日历（免手工导入，可读回与撤销）

```powershell
powershell -ExecutionPolicy Bypass -File scripts\win_calendar.ps1 doctor
powershell -ExecutionPolicy Bypass -File scripts\win_calendar.ps1 plan  -Json 产出\日程清单.json
powershell -ExecutionPolicy Bypass -File scripts\win_calendar.ps1 apply -Json 产出\日程清单.json
powershell -ExecutionPolicy Bypass -File scripts\win_calendar.ps1 rm    -Anchor LR-MI-XXXXXXXX -Apply
```


### 方案三：Windows 系统通知提醒（到点必响，不占日历）

```powershell
powershell -ExecutionPolicy Bypass -File scripts\win_remind.ps1 doctor
powershell -ExecutionPolicy Bypass -File scripts\win_remind.ps1 install              # 每机一次，注册通知身份
powershell -ExecutionPolicy Bypass -File scripts\win_remind.ps1 selftest -DelaySeconds 40
powershell -ExecutionPolicy Bypass -File scripts\win_remind.ps1 apply -Json 产出\日程清单.json
powershell -ExecutionPolicy Bypass -File scripts\win_remind.ps1 list
powershell -ExecutionPolicy Bypass -File scripts\win_remind.ps1 clear -Anchor LR-MI-XXXXXXXX -Apply
```


### 方案四：手工照单录入（兜底）

`plan` 的输出本身就是一份可读的清单（标题、时间、地点、每档提醒），复制到日历客户端或系统日历里逐条录入即可。宿主没有任何写入能力时用这条，不要在缺通道的情况下假装写入成功。

### Windows 侧的读回与撤销

`list` 与 `rm` 子命令依赖 EventKit，Windows 上按设计不可用（`ics` 是导出格式，没有回读能力）。Windows 上要撤销或核对已写入的日程，三条路：

1. 走 `.ics` 导入的：在日历客户端或系统日历里按正文中的「来福ID:」搜索后删除。
2. 走 `win_calendar.ps1` 的：`list -Days 60` 读回、`rm -Anchor <锚点> -Apply` 撤销，与 macOS 侧用法一致。
3. 走 `win_remind.ps1` 的：`list` 读回已排定的通知、`clear -Anchor <锚点> -Apply` 撤销（`-Prefix LR-MI-` 可批量清）。

## 七、撤销与核对

- 撤销：`rm --anchor <锚点> --apply`，事件与其全部提醒档位一并删除（先删精确锚点，再按「锚点-T」前缀清档位，不误伤同前缀的其他条目）。
- 核对：`list --days 60` 列出所有带 `LR-MI-` 前缀的条目，类型、时间、标题一览。
- 与 schedule-sync 技能共存：两边锚点格式相同，日程与提醒的写法一致；macOS 上用本模块写入的条目，schedule-sync 的 `list` 同样看得见，反之亦然。

## 八、别踩的坑

1. 不要用 AppleScript 操作 Calendar／Reminders——macOS 的 AppleScript 通道删除周期事件会静默失败，本模块固定走 EventKit。
2. 不要在 iCloud 账户上新建日历后立刻写入——同步未完成时写入会被回滚；容器由模块建在「本机」账户。
3. 不要把材料里的期限直接建成「当天提醒」了事——庭审与期限类必须走 7/3/1/0 四级，这是本工作流的既定节奏。
4. 撤销只按锚点操作，不要按标题搜索删除，手工创建的同类标题条目会被误伤。
5. 不要只看 `doctor` 里的「日历授权：已授权（可用：True）」就开写——把授权改成「仅写入」后这两行照旧显示可用，而读取已经被拒。判断标准只有结论行与 `ok` 字段。
